## 08-17-2026 — Experimental V2 Witness Routing First Pass

### Problem Reframed

The operational problem was not merely transcript parsing. A roughly 6.5-hour testimony artifact was still one giant object presented to an analyst or agent with the implicit request to understand everything at once. That made targeted legal and evidentiary procedures expensive, repetitive, and difficult to source precisely.

The new working hierarchy is:

`Proceeding -> witness index -> bounded witness block -> timestamped turns and procedural events`

Day 5 now deterministically resolves into 13 candidate witness blocks. For example, `witness_008` identifies Dr. Shah at `03:04:37-04:56:24`, making that portion of the source an addressable unit of work rather than forcing every downstream procedure to consume the entire day.

### Completed

- Integrated the experimental V2 first pass into the inbox compiler so every supported transcript discovered in `transcripts/inbox` receives the same deterministic structure pass after byte-for-byte preservation.
- Supported both observed Rev transcript shapes: Markdown turns with timestamp deep links and direct copy/paste plain-text turns with displayed timestamps. Direct copy/paste `.txt` intake is the expected path for later transcripts moving forward.
- Produced checksum-bound candidate witness blocks, boundary confidence, examination-phase runs, examiner candidates, jury-presence state, and procedural markers.
- Preserved source-line, media-timestamp, timestamp-seconds, and available Rev deep-link locators throughout the derived output.
- Kept all output explicitly `candidate_structure_only`; no statement becomes a verified fact, event, proposition, credibility finding, or database record.

### Architectural Consequence

The witness index is becoming a routing layer rather than only a table of contents. A later orchestrator can select a witness block, structure its examination, preserve significant procedure, identify domains of knowledge, and then invoke only relevant testimony-analysis skills.

The intended selective sequence is:

`witness detection -> examination structure -> procedural filtering -> substantive testimony extraction -> specialized legal/evidentiary procedures -> timestamp-linked structured output`

Potential specialized routes include fact-witness analysis, medical or expert testimony, impeachment and prior inconsistent statements, foundation, hearsay/source chains, and timeline evidence. Different witnesses should receive different procedures. A long block such as Dr. Shah's can first be internally mapped so later analysis targets relevant portions rather than repeatedly processing nearly two hours.

### Boundary

V2 remains under test. Witness identity, block boundaries, examination phases, jury state, and procedural classifications require review. Boundary confidence describes detected cues only and says nothing about credibility, truth, or evidentiary weight. The immutable transcript remains the source beneath every derived analytical layer, and every later output must retain its originating turn and timestamp/deep link.

The current inbox is intentionally mixed while testing: it contains Rev Markdown captures, direct copy/paste `.txt` transcripts, prior deterministic JSON outputs, and ChatGPT-produced notes derived from transcript material. Those notes remain useful case data but are not transcript source artifacts. Their normalization and relocation are deferred; no source or derived note was deleted during this pass.

### Observation

Several days of architecture uncertainty collapsed into a small deterministic parser once the correct intermediate object was identified. The legal-analysis skills did not primarily need a larger context window; they needed clean, addressable, provenance-preserving units over which to operate.
