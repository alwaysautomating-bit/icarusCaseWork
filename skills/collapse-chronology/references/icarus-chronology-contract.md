# Icarus Chronology Contract

Read this reference whenever `collapse-chronology` produces a structured bundle, maps results to Icarus records, or designs chronology persistence.

## Canonical source hierarchy

```text
Source
  -> represented by Source Artifact
      -> addressed through Source Segment + Source Locator
          -> used by extraction Activity
              -> generates reviewable knowledge objects
```

Do not use “source” as shorthand for all four levels.

For a parsed court packet:

- the complete preserved PDF is the **Source Artifact**;
- the court, filing, warrant, interview, device system, or other origin is the **Source** when known;
- each page or page region is a **Source Segment** with a typed page **Source Locator**;
- a confirmed court-packet document is a reviewed grouping of Source Segments; and
- LlamaParse output is a derived representation generated by a parsing activity.

## Icarus object mapping

| Chronology concern | Icarus representation | Integrity rule |
| --- | --- | --- |
| Attributed statement | `Claim` | Never flatten speaker, basis, or qualifiers |
| Normalized state of affairs | `Proposition` | Has no automatic truth or verification status |
| Possible occurrence | `event_candidates` / Event Candidate | Remains reviewable |
| Operationally admitted occurrence | `events` / Reviewed Event | Requires explicit review and linked evidence |
| Claimed event time | `temporal_assertions` / Temporal Assertion | Preserve raw language, precision, and source |
| Possible entity reference | `entity_mentions` | Canonical identity resolution remains separate |
| Event/order/information relation | `knowledge_relationships` | The edge is reviewable and source-backed |
| Extraction concern or gap | `knowledge_flags` | Agent-created flags begin as proposed |
| Generated grouping/context | `knowledge_items` | Must cite exact Source Segments |
| Processing or review operation | `provenance_activities` | Record software/model/configuration and actor |
| Derivation or attribution edge | `provenance_relations` | Use the implemented PROV relation vocabulary |
| Record-entry order | `case_ledger.logical_order` | Database allocated; never model generated |
| Human support evaluation | `Verification Assessment` | Separate from extraction and acceptance |
| Cross-source comparison | Reconciliation Layer | Never mutate original lane-specific Claims |
| Reusable “known” | Existing reviewed objects | “Known” is a UI label, not a new entity type |

## Three-clock field mapping

### Clock 1 — case / knowledge time

```yaml
case_ledger:
  logical_order: database_allocated
  operation: created | versioned | reviewed | corrected | superseded | flagged
  actor_user_id: authenticated_researcher_or_null
  system_agent: named_system_or_null
  created_at: server_timestamp
```

Clock 1 answers when the information entered or changed in Icarus. It does not describe source order or real-world occurrence time.

### Clock 2 — IRL / event time

```yaml
temporal_assertion:
  raw_temporal_language: exact_source_wording
  asserted_start: timestamp_or_null
  asserted_end: timestamp_or_null
  asserted_date: date_or_null
  asserted_time_of_day_start: local_time_or_null
  asserted_time_of_day_end: local_time_or_null
  time_of_day_band: text_or_null
  precision: implemented_precision_value
  qualification: implemented_qualification_value
  qualifier_text: exact_qualifier_or_null
  sequence_language: exact_relative_wording_or_null
  lower_bound_event_candidate_key: candidate_key_or_null
  upper_bound_event_candidate_key: candidate_key_or_null
  asserted_by_raw: source_attribution
  source_segment_ids: []
  extraction_confidence: 0.0
```

Unknown and relative-only time must not receive a fabricated absolute timestamp. A document's filing date, packet position, or transcript timestamp is not Clock 2 unless the source expressly uses it as occurrence time.

### Clock 3 — provenance / information time

Represent Clock 3 with:

- ordered Claim Attribution roles;
- Claim and Source Lineage;
- Source Artifact capture and generation metadata;
- `provenance_activities` with start/end times; and
- `provenance_relations` connecting activity, artifact, segment, extraction, and review.

Example information path:

```text
Patrick
  -> told investigator
Investigator
  -> recorded assertion in affidavit
Affidavit page Source Segment
  -> parsed by LlamaParse activity
Chronology activity
  -> generated Claim and Event Candidate
Researcher review activity
  -> accepted, amended, rejected, or deferred candidate
```

The Claim is not attributed to LlamaParse. The extraction candidate is generated by the LlamaParse/chronology activity and derived from the affidavit segment.

## Lamppost contract

The lamppost gives durable coordinates for asking “what is this?” and “where did this come from?” It is not a temporal estimate.

```yaml
identity:
  id: stable_uuid_after_persistence
  object_code: case_scoped_human_code
  candidate_key: temporary_bundle_key_before_persistence
source_address:
  source_artifact_id: stable_uuid
  source_segment_ids: []
  source_locators: []
record_address:
  logical_order: database_allocated_after_persistence
```

Never use a page number without its Source Artifact, a timestamp without its Source Segment, or a temporary extraction label as a persistent ID.

## State and supersession projections

A transition is derived for readability from existing objects:

```yaml
transition:
  subject_ref: entity_or_proposition_ref
  before_state_claim_keys: []
  event_candidate_key: local_event_key
  after_state_claim_keys: []
  effective_temporal_assertion_keys: []
  status: candidate | probable | disputed | unresolved
  source_segment_ids: []
```

“Probable” describes the projection's current analytical confidence, not a Verification Assessment. Persist the underlying Claims, Event Candidate, Temporal Assertions, and relationships; do not invent a transition table merely to match this projection.

Supersession requires an explicit replacement, withdrawal, correction, invalidation, or authoritative scope change. A newer mention is not enough. Preserve both objects, propose a `supersedes` or `corrects` relationship, and let the governed review path create the Clock 1 `superseded` or `corrected` ledger operation.

## Forbidden collapses

Never collapse:

- Source into Source Artifact;
- Source Artifact into Source Segment;
- Claim into Proposition;
- Claim or Proposition into Event;
- Event Candidate into Reviewed Event;
- document date into IRL event time;
- transcript timestamp into IRL event time;
- source order into case ledger order;
- later repetition into independent corroboration;
- model extraction into source attribution;
- human acceptance into verification;
- a topological presentation order into one proven total chronology; or
- a user scope assumption into a universal evidentiary rule.

## Persistence gate

Before any write:

1. Validate every exact Source Segment and Source Locator.
2. Validate enumerations against the current code and migrations.
3. Confirm candidate references resolve within the same Case.
4. Record the extraction activity and configuration.
5. Use the deterministic compiler for stable UUID/object-code allocation and the governed atomic persistence path for validation and Clock 1 allocation.
6. Leave consequential objects pending until an authorized human Review Decision.
7. Preserve the full rejected, amended, corrected, and superseded history.
