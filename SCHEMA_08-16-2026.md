### Current security and epistemic constraints

- Case membership is database-backed; user-editable metadata is never authorization input.
- Public mutation functions either execute as the caller or delegate to fixed-search-path private cores that re-authorize the actor and validate case ownership of linked objects.
- Direct authenticated writes to governed candidate/review/version tables are denied where mutations require an RPC.
- Candidate review does not silently create canonical events or resolve entity identity.
- Trial-index records are permanently `navigation_only` and cannot become evidence, claims, findings, canonical events, or reconstruction input through their persistence function.
- Courtroom/source timestamps remain testimony provenance and are never substituted for real-world event time.

The sections below preserve the earlier base-schema record. When they differ from this checkpoint or the migrations, the committed migration chain is controlling.

## Historical Base Inventory (through URL intake)

- `cases`: bounded workspace, owner user, purpose, public-record cutoff, and incident anchors.
- `case_members`: authenticated user membership and owner/researcher/reviewer/viewer role within a case.
- `source_artifacts`: immutable object identity, checksum, provenance, media type, and authorization.
- `source_segments`: canonical source-text spine. `exact_text` preserves the searchable transcript/source text; `locator`, timestamps, ordinal, proceeding, speaker, and artifact relationships retain its exact typed address and provenance. Search indexes must derive from this table rather than a testimony surrogate.
- `claims`: attributed assertions with claimed-event time separate from statement time and review status.
- `review_decisions`: append-only human disposition, rationale, authenticated reviewer user, and time.
- `events`: reviewed observable occurrences promoted from accepted claims; one event cannot be silently promoted twice.
- `evidence_snapshots`: versioned manifest hash for reproducible projections.
- `snapshot_artifacts`: immutable membership of artifacts in a snapshot.
- `schema_migrations`: local migration ledger.
- `entities`: durable case-scoped identity for people, organizations, locations, devices, proceedings, and system nodes.
- `entity_aliases`: reversible source-specific names attached to a canonical entity.
- `artifact_provenance`: explicit originator, publisher, custodian, or submitter roles between entities and artifacts.
- `claim_lineage`: typed origin, quotation, paraphrase, repetition, or derivation edges between distinct claims.
- `contradictions` and `contradiction_claims`: unresolved evidentiary tensions and their linked accounts.
- `audit_events`: append-only authenticated actor user, action, subject, detail, and timestamp trail for consequential mutations.
- `contradiction_dispositions`: one evidenced terminal disposition per contradiction; non-cancellation dispositions require a linked evidence claim.
- `saved_research_views`: named case-scoped projections over all, 90-day, 30-day, or incident-window records.
- `sources`: evidentiary source identity, family, testimony/documentary/direct-evidence lane, origin, possession, and completeness independent of file representation.
- `evidence_intakes`: submitted and canonical URL, capture metadata, checksum, parser identity/status, exact-duplicate relation, error state, and authenticated submitter.
- `source_lineages`: canonical source lineage and canonical artifact link used to prevent repeated representations from masquerading as independent sources.
- `propositions`: review-required normalized proposition candidates shared without mutating the source claim.
- `claim_attributions`: ordered entity chains such as reported-by, testified-by, and transcribed-by.
- `media_references`: separately identified embedded media that is referenced but not represented as possessed.
- `evidence_acquisition_records`: known-but-unpossessed exhibits and underlying records, with discovery timestamp and acquisition status.
- `claim_support`: reconciliation-owned, lineage-aware support/conflict relations; authenticated intake users have read-only access.
- `verification_assessments` and `verification_assessment_claims`: append-preserving post-intake verification state and its supporting/conflicting claims; authenticated intake users have read-only access.
- `event_claims`: multi-claim event relationship retained alongside the existing single promoted-claim compatibility path.

## Purpose

Persist the minimum authoritative evidence substrate for the first source-linked vertical slice. Claims and events remain distinct records connected by an explicit reviewed promotion.

## Relationships

- Case 1:N SourceArtifact, Claim, Event, EvidenceSnapshot
- AuthUser N:M Case through CaseMembership; each Case has one owner user
- SourceArtifact 1:N SourceSegment
- SourceSegment 1:N Claim
- Claim 1:N ReviewDecision
- Accepted Claim 1:0..1 Event
- EvidenceSnapshot N:M SourceArtifact

## Indexes

- Unique `(case_id, sha256)` prevents duplicate artifact identities per case.
- `claims(case_id)` supports review queues.
- Unique `events(promoted_from_claim_id)` prevents duplicate promotion.
- `events(case_id, event_time_start)` supports timeline projection.
- `entities(case_id)` supports identity resolution.
- `contradictions(case_id, status)` keeps unresolved work visible.
- `audit_events(case_id, occurred_at)` supports authority-log retrieval.
- Unique `cases(owner_user_id, workspace_key)` makes default-case creation safe across concurrent first loads while leaving room for future named workspaces.
- Unique `(artifact_id, ordinal)` preserves transcript order, and timestamp checks reject backward interval ends.
- Source/intake/lineage, speaker, proposition, attribution, acquisition, support, and verification indexes support the implemented intake and later reconciliation queries.

Local `supabase db reset`, migration listing, authenticated browser writes, and the security advisor now provide execution evidence for that migration.

Known schema debt: `src/db/schema.ts` reflects the earlier portable/local model and is not fully synchronized with the authoritative Supabase migration. It must be reconciled or explicitly retired before the next schema change.

## 08-16-2026 — Testimony URL Intake Migration Implemented

Migration `20260817035154_testimony_url_intake.sql` implements the planned testimony model and extends `source_artifacts`, `source_segments`, and `claims` rather than duplicating them. A composite foreign key requires each Claim to share its Source evidence lane. The `commit_testimony_url_intake(jsonb)` security-invoker function performs the domain write atomically, accepts testimony only, rejects reconciliation/verification payload keys, and records exact-checksum retries as duplicate intakes that reuse the original artifact graph.

All new exposed tables use case-membership RLS and explicit authenticated grants. `claim_support` and verification tables expose SELECT only to authenticated application users; service-role administration remains server-only and must never enter the application client. The migration aborts when legacy artifacts or claims exist without an explicit classification plan instead of silently assigning an evidence lane.

The migration replays from zero in Supabase and PGlite contract tests. The remaining schema debt is the older `src/db/schema.ts` reference, which must be reconciled or formally retired before another broad schema slice.

## Migration Policy

- All schema changes are versioned, reviewed, and applied through controlled migrations.
- The active local and deployment database contract is the versioned Supabase migration set under `supabase/migrations/`.
- The legacy PGlite adapter and ordered local SQL files remain reference fixtures, not the active runtime migration authority.
- The deployed database uses Supabase unless a documented constraint activates the Neon fallback.
- If Prisma is introduced later, production migration execution must use `prisma migrate deploy`.
- `prisma db push` is prohibited as a production migration strategy.
